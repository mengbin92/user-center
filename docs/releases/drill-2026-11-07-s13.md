# S13 演练记录：备份恢复与升级回滚

> 时间：2026-11-07（UTC+8）
> 环境：本机 Docker 29.9.2，MySQL 8.4 + Redis 7，compose 全栈，数据量为空库 + 1 组织 / 1 用户 / 2 审计 / 2 Outbox
> 脚本：`scripts/dr/restore-drill.sh`、`scripts/dr/upgrade-rollback-drill.sh`（可重复执行，失败保留工作目录与日志）
> 结论：**两个演练均通过**，但演练过程中发现并修复了一个真实缺陷（见 §3）。

这份文档记录的不是"照文档做了一遍"，而是"照文档做时发现文档和代码哪里错了"。数值只能说明流程可跑通，不能外推到生产容量。

## 1. 备份 → 清库 → 恢复 → 冒烟

```
scripts/dr/restore-drill.sh --work-dir /tmp/uc-drill-restore
```

| 步骤 | 实测 | 说明 |
|---|---|---|
| `mysqldump --single-transaction --routines --triggers --events` | 67,529 B / **150–200 ms** | 断言 dump > 20 KB，防止 mysqldump 把错误写进文件却被当成成功 |
| `DROP DATABASE` + 重建 | **341–371 ms**，39 张表 | 用 drop 而不是删卷，证明"仅靠 dump 就够" |
| 导入恢复 | **366–637 ms** | |
| 服务自愈（**未重启容器**） | **831–1,392 ms** | 连接池自己重连；重启会掩盖这一点 |
| 恢复后 `scripts/e2e/smoke.sh` | 通过 / **775–1,144 ms** | 路线图的硬性验收 |
| 数据一致性 | **10 张表逐表一致** | 比对行数 + `MAX(id)`，只比行数会漏掉尾部被截断 |

数值是本机 3 次执行的区间，不是基准测试。它们几乎全是固定开销（容器启动、连接重建、shell 往返），**不能外推到生产数据量**；要估真实 RTO 请用 `scripts/bench` 的规模数据重跑脚本。

断言覆盖：users、user_credentials、organizations、organization_members、iam_sessions、iam_roles、password_history、iam_audit_events、event_outbox、schema_migrations。fingerprint 按表是否存在动态生成，因此同一脚本能跑在旧 schema 上。

**意外结论（已写进 `docs/operations.md` §7.1）**：会话存在 MySQL，恢复备份会让备份时刻有效的会话**复活**，包括后来被撤销的；Redis 里的挑战、step-up 凭据、限流计数不备份且自然重建。因此因安全事件回滚后必须显式撤销会话，不能假设"恢复 = 踢下线"。

## 2. v0.6.1 → 当前版本 → 回滚

```
# 旧镜像来自 tag 的 worktree（脚本会检查并给出构建命令）
git worktree add --detach /tmp/uc-v0.6.1 v0.6.1
(cd /tmp/uc-v0.6.1 && docker build -t user-center:v0.6.1 .)
scripts/dr/upgrade-rollback-drill.sh --work-dir /tmp/uc-drill-upgrade
```

| 步骤 | 实测 |
|---|---|
| v0.6.1 迁移步数 | 58 |
| 升级到当前（13 个迁移文件） | 58 → 64 步 / **341–352 ms** |
| 新版就绪 | **44–91 ms** |
| 升级后数据 | 8 张表**无丢失**（冒烟自身新增的组织使计数增长，故此处不比相等） |
| 回滚总耗时 | **1,081–1,243 ms**，其中数据库恢复 766–803 ms |
| 回滚后数据 | 8 张表**逐表一致**（在冒烟写入之前比对，避免被演练自身流量污染） |
| 回滚后 smoke | 通过（`--skip-readyz`，因为旧版本没有该端点） |

不可逆 DDL 由脚本从迁移文件自动扫描（当前 1 处：`006_org_iam.sql` 的 `DROP INDEX uk_iam_roles_code`），避免文档写死后与实际迁移漂移。

### 额外实测：只回退镜像、不恢复数据库

这是运维最容易做的动作，所以单独验证。结论：**旧二进制能启动、能登录、能过 smoke**，因为 012/013 新增列都是 `NULL` 或带 `DEFAULT`，旧 ORM 用显式列清单不会碰到它们。但这不是契约，是巧合：

- 新版改密码 → 切回旧版再改一次密码：HTTP **200**，`password_history` 行数**没有增加**，`password_changed_at` **没有更新**。
- 即"禁止复用最近 N 次密码"在回退窗口内静默失效，且零报错。
- 组织约束、委派 context 等新表/新列在旧版视角下完全不参与判定，等于回退窗口内 SoD 全部暂停。

**因此唯一无条件安全的回滚路径是：旧镜像 + 恢复升级前备份库。** 详见 `docs/operations.md` §7.3。

## 3. 演练发现的真实缺陷（已修）

| # | 发现 | 修复 |
|---|---|---|
| F1 | `/healthz` 是静态 `{"status":"ok"}`，不查任何依赖，却被 `docker-compose.yml` 的 healthcheck 当作健康判断。`DROP DATABASE` 后容器仍报 healthy，负载均衡会继续把流量打给一个连不上的实例 | 新增 `/readyz`（MySQL 必需、Redis 仅报告），compose healthcheck 切到 `/readyz`；`/healthz` 保持纯存活探针 |
| F2 | 初版 `/readyz` 用 `PingDatabase` → `PingContext` 发 `COM_PING`，**库被删了也返回成功**，演练第二步仍然假绿 | `PingDatabase` 改为执行 `SELECT COUNT(*) FROM schema_migrations`，schema 缺失即失败；`usercenter_dependency_up` 指标同步变准 |
| F3 | compose 镜像名硬编码 `user-center:latest`，回退必须改文件（改文件会让清单偏离实际部署，且下次 pull 被覆盖） | 参数化为 `${USER_CENTER_IMAGE:-user-center:latest}` |
| F4 | 旧版（v0.6.1）没有 `/readyz`，SPA fallback 对未知路径返回 200 + `index.html`；只按状态码判断的 `wait_ready` 会在旧版上**假绿灯** | `wait_ready` 改为校验响应体含 `"status":"ok"`；旧版本用 `wait_legacy_ready`（`/healthz` + 真实 SQL 查询） |
| F5 | `smoke.sh` 新增 `/readyz` 断言后，回滚到旧版本的 smoke 会失败 | 增加显式 `--skip-readyz` 开关，仅升级回滚演练在旧版阶段使用；静默省略会掩盖真实回归 |

附带：`scripts/e2e/smoke.sh` 增加 `/readyz` 断言；`internal/obs/ready_test.go`（3 条）与 `internal/server/probe_test.go`（3 条）锁定两个端点的职责分离。

**一个刻意的限制**：回滚到 v0.6.1 后，当前 compose 的 healthcheck 仍指向 `/readyz`，旧版会以 SPA fallback 的 200 让它显示 healthy——即回滚期间 healthcheck 再次变成假绿。这是"旧镜像 + 新清单"组合的固有代价，不单独给旧版打补丁；正确做法仍是 §7.3 的"旧镜像 + 恢复备份库 + 旧清单"。
