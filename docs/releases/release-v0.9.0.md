# v0.9.0 · 2026-11-07

上一版：[v0.8.0](./release-v0.8.0.md) · 范围：[V2.5 路线图](../roadmap-v2.5.md) W5（S12）

**版本判定：MINOR（v0.8.0 → v0.9.0）。** 新增组织域职责分离与委派能力（4 个 API、1 个前端 tab、2 个权限码），并修复一个安全缺口（组织分配此前完全跳过约束与委派校验）。有 **1 个数据库迁移**（`013`），无破坏性契约变更。

主题是**把平台已有的治理机制补到租户域**。组织上下文从 V2.3 起有独立的角色、授权与审计，但互斥角色对、角色数量上限、委派这三样一样都没有——平台侧的 SoD 规则在租户内是空转的，而平台并不知道。

## Added

### 组织域职责分离（S12）

- 组织约束 CRUD：`GET/POST/PATCH/DELETE /api/v1/orgs/{id}/iam/constraints`，支持 `mutual_exclusion` 与 `max_roles`。
- 迁移 `013`：`iam_role_constraints` 与 `iam_delegations` 增加 `(context_type, context_id)`。**`DEFAULT` 即回填**——存量行自动成为平台策略，无需 `UPDATE`，重跑也不会把行搬到别的上下文。
- 两个新权限码：`organization.iam.constraint.read`（owner + admin）、`organization.iam.constraint.manage`（仅 owner）。约束是治理动作，与"给成员分配角色"分开：能改规则的人比能执行规则的人权力更大。
- 收紧约束需要显式确认：响应返回 `violating_assignments`；有违规时写入被拒（`ORGANIZATION_POLICY_VIOLATIONS_PENDING`），必须带 `acknowledge_violations` 重试。
- 组织成员移除时，其角色分配与**双向**委派（作为 manager 与作为 target）在同一事务内软失效。
- 前端组织详情页新增「职责分离」tab：列表、新建（两步：编辑 → 确认）、删除，违规时给出明确警告。

### 委派上下文隔离

- `DelegationFilter` 增加 `Context`，`CreateDelegation` 写入上下文。平台委派无法批准组织分配，组织委派无法影响平台决策。
- 不传上下文时默认 `platform`，与存量行语义一致。

## Changed

- 组织分配现在会执行约束校验（此前完全没有）。行为上只会**变严**。
- 组织成员**不能给自己授权**（`ORGANIZATION_SELF_GRANT`）。此前没有这条限制。

## Fixed

- **组织分配绕过平台 SoD**：`OrgIAMUsecase.AssignRole` 既不调 `CheckConstraints` 也不调 `checkDelegation`，组织管理员可给同一成员授予互斥职责、无限叠加自定义角色。这是 V2.4 遗留的缺口，现在补上。
- **移除成员后仍可被授权**：撤销分配时未处理委派，被移除的成员仍可能通过残留委派获得角色。现双向软失效。

## 升级注意

1. **必须执行迁移**：`013_org_sod_delegation.sql` 给两张表加列。compose 部署走 `migrate` 一次性服务；手工部署需先跑 `migrate` 再启动新版本（代码会按 `context_type` 过滤，先上代码会读到空值行）。
2. **组织分配会变严**：如果某租户此前依赖"无限叠加角色"，升级后新增分配会按该组织已定义的约束执行。存量分配不追溯清理。
3. **回滚代价**：删两列即可回到旧 schema，但组织约束与组织委派记录会一并丢失。先备份。
4. **平台管理员不再能看组织约束**（本版起也没有过）：`isPlatformAdmin` 在 `orgGuard` 里是放行旁路，若给约束开口等于绕过租户治理。紧急处置走组织 owner 账号。

## 三个设计文档被代码推翻的点

评审与实现过程中，有三处原本写在设计里的断言经代码验证为错，均已修正文档并留痕（`docs/design/org-sod-delegation.md` §0）：

| # | 原设计 | 实际 | 后果 |
|---|---|---|---|
| F1 | "平台约束与组织约束求交合并" | 平台约束引用平台角色 ID，组织决策携带组织角色 ID，ID 空间不相交 → 平台约束在租户内**永远通过** | 结论（租户不能放宽平台）不变，但理由是**结构性隔离**而非合并求值。补了回归测试锁住这条性质 |
| F2 | 违规分配"在下次登录/激活时失效" | 组织权限**每次请求重算**，不读会话激活角色 → 收紧规则会让成员**立即**失去访问 | 写入改为必须确认 + 返回影响人数，前端明确告知"立即" |
| F9 | `max_roles` "只计自定义角色"，`0` = 只用内置角色 | 它是"`role_ids` 范围内最多几个"；`role_ids` 为空时约束整条被跳过；`max_count<=0` 被校验拒绝 | 删除设计中杜撰的租户专用计数口径，完全复用平台校验 |

## 已知限制

- **跨上下文 SoD 不存在**："同一人不能既审批又付款，不论哪个租户"用角色组合表达不了，需要把约束对象换成 operation 集合（另一个模型）。
- **约束校验角色组合，不校验实际能力**：两个角色若授权内容等价，互斥仍按"两个不同角色"处理。
- **平台管理员无组织约束入口**，这是刻意的。
