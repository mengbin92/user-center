# 性能基线

> 采集时间：2026-11-06 · 基线 commit：`f3b26c4`（v0.7.0 W1/W2 起点）· 脚本：[`scripts/bench/`](../scripts/bench/)
>
> 这份文档只描述**这台机器上的**单实例表现。它不是容量承诺，也不能直接外推到生产；
> 它的用途是给后续改动一个可复现的对照点。

## 1. 环境

| 项 | 值 |
|---|---|
| 主机 | Apple M5，16 GB RAM，macOS 27.0.1 |
| Docker VM | 10 CPU / 8 GB（MySQL 容器运行于此） |
| MySQL | 8.4.11（`mysql:8.4`） |
| Go | go1.27.3 darwin/arm64 |
| 压测器 | k6 v2.3.0，**与服务同机** |
| 服务配置 | `scripts/bench/config.mysql.yaml`：`max_open_conns=20`、`max_idle_conns=10`、Redis 未启用（内存回退）、metrics 关闭 |

## 2. 复现

```bash
scripts/bench/run.sh                          # 16 VUs，5 个场景，30s/场景
scripts/bench/run.sh --vu 32 --scenarios me,admin,org
```

脚本自己起 MySQL 容器、迁移、造 24 个账号、起服务、建会话池、跑 k6、输出表格，
退出时停服务。细节与偏差说明见 [`scripts/bench/README.md`](../scripts/bench/README.md)。

## 3. 主基线（16 VUs）

| 场景 | VUs | 时长 | 请求数 | QPS | P50 (ms) | P95 (ms) | P99 (ms) | 失败率 |
|---|---|---|---|---|---|---|---|---|
| `context`（未认证） | 8 | 20s | 115,639 | 5,782 | 1.23 | 1.87 | 3.18 | 0% |
| `me`（授权投影） | 16 | 30s | 23,665 | 788 | 18.91 | 29.06 | 42.75 | 0% |
| `admin`（用户列表） | 16 | 30s | 5,280 | 176 | 88.71 | 111.13 | 137.42 | 0% |
| `org`（成员列表） | 16 | 30s | 26,349 | 878 | 17.08 | 23.97 | 37.42 | 0% |
| `login`（限流中） | 8 | 20s | 195,168 | 9,758 | 0.88 | 1.82 | 2.28 | 50%（429） |

`login` 的 50% 失败率是预期：该场景每轮发一次登录，几秒内就打满 `30 次/5 分钟/IP`
的硬限流，之后的请求全部 429。这个数字说明的是**限流器本身很便宜**（9,758 req/s 含一半拒绝），
**不是**登录吞吐能力。

## 4. 并发梯度

同一份脚本、同一配置，只改 VUs：

| VUs | `me` QPS / P95 | `admin` QPS / P95 | `org` QPS / P95 |
|---|---|---|---|
| 8 | 574 / 17.0 ms | 150 / 64.9 ms | 692 / 14.3 ms |
| 16 | 788 / 29.1 ms | 176 / 111.1 ms | 878 / 24.0 ms |
| 24 | 610 / 65.3 ms | 191 / 147.2 ms | 991 / 29.7 ms |
| 32 | 786 / 50.1 ms | 190 / 192.0 ms | 1,002 / 39.8 ms |

读法：

- `org` 到 32 VUs 仍在上升（692 → 1,002 QPS），**未探到上限**。
- `me` 在 16 VUs 后饱和在约 780 QPS，此后 QPS 不增、延迟随 VU 增长。
- `admin` 在 8 VUs 就接近饱和（150 → 190 QPS），P95 从 65 ms 线性涨到 192 ms。
- 24 VU 的 `me` 掉到 610 QPS 属于测量噪声：压测器与服务抢同一颗 CPU，同机复测波动可达 20%。
  判断趋势要看 8 / 16 / 32 三点，不要单独引用 24。

## 5. 首个发现：`max_open_conns: 1` 吃掉 3.5–4 倍容量

`configs/config.dev.yaml` 里 `max_open_conns: 1`（SQLite 必须如此）被最初几轮基线直接继承，
于是所有请求串行在**一个** MySQL 连接上。表现很有迷惑性：QPS 从 2 VUs 就不再增长，
延迟随 VUs 线性上升，看起来像"数据库慢"，实际是连接池只有一个。

同一台机器、同一条命令，只换配置：

| 场景 | 池 = 1 | 池 = 20 | 提升 |
|---|---|---|---|
| `context` | 2,226 QPS / 7.63 ms | 5,782 QPS / 1.87 ms | 2.6× |
| `me` | 206 QPS / 111.8 ms | 788 QPS / 29.1 ms | 3.8× |
| `admin` | 47 QPS / 485.7 ms | 176 QPS / 111.1 ms | 3.7× |
| `org` | 296 QPS / 80.0 ms | 878 QPS / 24.0 ms | 3.0× |

因此基准使用独立的 [`scripts/bench/config.mysql.yaml`](../scripts/bench/config.mysql.yaml)，
不修改 dev 配置。**部署到 MySQL 时若沿用 SQLite 的连接池设置，容量会少约四分之三。**

## 6. 单实例安全水位

以 P95 < 100 ms 为界（内部管理面目标）：

| 场景 | 安全水位 | 超过该水位后的表现 |
|---|---|---|
| `me` | ≈ 780 QPS / 16–32 VUs | QPS 不再上升，延迟随并发继续增长 |
| `org` | ≈ 878 QPS / 16 VUs（未探底） | 32 VUs 仍线性增长，说明还没撞到软上限 |
| `admin` | ≈ 150 QPS / 8 VUs | P95 在 24 VUs 达 147 ms、32 VUs 达 192 ms |

扩容判据（先优化再扩容）：

1. `admin` 是最先触顶的端点。**8 VUs 就到 150 QPS、单请求 P50 52.7 ms** 处理 24 行列表，
   这个成本明显偏高，先做 `EXPLAIN` 定位（S5），大概率能拿回数倍而不是加机器。
2. `me` 每次请求固定 6 次读 + 1 次写（会话、用户、角色、凭据、设置、`Touch`），
   属于"会话校验 + 权限投影"的结构性成本，需要靠缓存或批量查询解决，不是加 CPU 能解决的。
3. 横向扩容（多实例 + 负载均衡）在当前单实例尚未打满 300 ms 延迟线的前提下没有收益。

## 7. 偏差：读数字前必看

1. **压测器与服务同机**：k6 和被测服务争抢同一颗 CPU 与回环网络，绝对 QPS 偏低。
2. **基准账号是 root**：`admin-rescue bootstrap` 只能造 root，每次请求都要展开完整权限集，
   `me` / `admin` 的数字是**权限计算的最坏情况**，普通 `member` 账号会更低。
3. **会话池 24 个**：VU 超过 24 时部分 VU 共享会话（本次 32 VUs 有 8 个共享），
   这些请求会在 `iam_sessions` 的同一行上串行更新，数字偏悲观。
4. **MySQL 未调优**：容器默认参数（`innodb_buffer_pool_size` 等）未调整，生产会配不同参数。
5. **无 Redis**：走内存回退，会话校验的缓存命中路径没被覆盖；生产有 Redis 时 `me` 应更快。
