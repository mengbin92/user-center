# 安全设计

## 1. 资产与信任边界

| 资产 | 边界 |
|---|---|
| 密码摘要、TOTP 密文、恢复码摘要 | 仅 `user_credentials` / `identity_mfa`；任何普通查询不返回 |
| 会话令牌 | 仅浏览器 HttpOnly Cookie 与服务端哈希；不返回 JSON、不写日志 |
| 验证码 | HMAC 后存 Redis/内存；邮件正文外不落库 |
| 授权事实 | MySQL 为权威；前端只消费 `/me/authorization` 投影 |
| 审计 | 追加写；普通管理员不能删除 |
| 接入客户端凭据 | 仅创建/轮换时展示；DB 存摘要；gRPC Bearer 与方法白名单 |

浏览器、反向代理、数据库、Redis、SMTP 均视为独立信任域；跨域只通过明确契约。

## 2. 控制清单

| 威胁 | 控制 |
|---|---|
| 会话窃取/重放 | 随机不透明令牌、HttpOnly/SameSite、DB 哈希、身份版本校验、空闲+绝对过期、撤销全部会话 |
| CSRF | 双提交 Cookie + 中间件强制 header 校验（所有非 GET `/api/v1`） |
| 会话固定 | 登录/完成 MFA 均生成新会话，不复用匿名标识 |
| 暴力破解 | 登录 IP/用户限流；MFA 5 次失败锁定 5 分钟；挑战验证码 10 次尝试上限 |
| 账号枚举 | 登录统一“用户名或密码错误”；密码重置统一成功响应；注册邮箱冲突返回挑战失败 |
| 验证码重放 | 单次消费 + DB `(challenge_id,purpose)` 唯一完成记录 |
| TOTP 重放 | 持久化 `last_step`，拒绝已使用时间步 |
| 恢复码泄露 | 仅展示一次；SHA-256 存储；使用即删除 |
| 越权 | 操作权限 + Scope 边界 + 显式 deny + 有效期 + 约束；资源 owner 执行点校验 |
| 数据范围绕过 | 列表/详情/导出/会话接口统一 Scope 过滤；受限管理员不能通过分页/导出扩大范围 |
| 并发覆盖 | 用户 revision、policy revision、角色/分配 revision CAS |
| 高风险操作 | Step-up（主认证 + 第二因素，绑定 session 与 identity_version，5 分钟） |
| 管理员未绑定 MFA | 管理授权入口强制 `MFA_ENROLLMENT_REQUIRED`，但保留安全中心完成绑定 |
| 初始密码 | `password_change_required` + 中间件阻断 `/admin/*`，改密后清除 |
| 弱密码 | 策略可配（长度、字符类数、历史条数、有效期）；四处入口共用 `ValidatePassword`；违反返回 `PASSWORD_POLICY_VIOLATION` |
| 密码复用 | `password_history` 只存 bcrypt 摘要，按策略窗口折叠；改密/重置/首设都写入 |
| 会话膨胀 | 每用户并发会话上限（默认 10），超限按最久未活跃强制失效，登录响应回传回收数量 |
| 高权限被脚本刷 | 统一写接口限流（按 用户/接入客户端 计数，默认 120 次/分钟）；导出、批量分配、邀请 10 次/分钟 |
| 第三方登录 | 单次 state（Redis + HttpOnly Cookie）、服务端 code 交换、不按邮箱自动合并、已启用 MFA 时仍要求第二因素 |
| 接入客户端 | 凭据只存 SHA-256、一次性展示、按 gRPC 方法白名单校验、可轮换/停用 |
| Webhook | HMAC-SHA256 原始 body、至少一次投递、重试退避、消费端按 event_id 去重；公网回调必须 https，拒绝链路本地/未指定地址 |
| OIDC Provider | 授权码一次性消费、PKCE S256、redirect_uri 精确匹配、RS256、短时 access/refresh token、客户端密钥摘要 |
| OIDC 同意 | 一次性服务端 request handle（仅存哈希、绑定用户与 10 分钟有效期）；打开同意页不签发授权码，用户决意后才签码；scope 扩张/`prompt=consent` 重新征询；`prompt=none` 返回 `interaction_required`；用户可在 `/me/oidc-consents` 撤销 |
| RP-initiated logout | `post_logout_redirect_uri` 精确匹配客户端白名单；无效/过期 hint 与缺失 hint 行为一致，`client_id` 与 hint `aud` 不一致时拒绝回跳；无论回跳是否被接受都先撤销本地会话并清理 Cookie，重复调用幂等 |
| 组织邀请 | 令牌只在邮件中出现、DB 存哈希、默认 72 小时（`ORG_INVITATION_TTL_HOURS` 可配）；接受要求登录且账号邮箱归一化后完全相等；不匹配/不存在返回同一 404；不自动建号；单组织待接受邀请有上限；列表含被邀请人邮箱，因此与创建/撤销同要求 `organization.member.manage` |
| 租户审计导出 | 复用平台导出任务与下载签名；`organization_id` 固定在过滤条件和任务行上；跨租户/策略版本变化/会话变化均返回 404；CSV 公式前缀转义 |
| 组织域事件 | 与业务事务同提交；载荷只含 ID/revision/角色码，不含邮箱、昵称；订阅按 `event_type` 过滤，消费端按 `event_id` 去重并按 `aggregate_revision` 判新旧 |
| 内部 gRPC 登录 | 凭据只在服务端 gRPC 传输；方法白名单 + 接入客户端鉴权；复用 HTTP 登录限流与失败计数；MFA 挑战绑定应用与身份版本且单次消费；会话 audience 绑定调用方应用；审计记录 `actor_service_id` |
| 用户名修改 | Step-up + 当前密码 + `expected_revision` CAS；归一化唯一性与保留字同注册路径共用；管理端不提供改名接口；审计记录前后值 |
| 组织创建配额 | 默认关闭；开启后在事务内对该用户的组织行加锁计数；超限返回 `ORGANIZATION_QUOTA_EXCEEDED` 并写拒绝审计；平台管理员豁免 |
| 组织成员 | 组织角色校验、最后 owner 保护、平台管理员特权、成员邮箱按角色脱敏、变更 revision CAS；归档/成员增改删要求 Step-up |
| 组织职责分离 | 约束/委派按 `(context_type, context_id)` 隔离；引用的角色必须同上下文且未归档；成员不能给自己授权；收紧需显式确认；变更写组织审计与 Outbox |
| 审计缺失 | 敏感写与业务事务同提交写审计；安全事件独立表 |
| 密钥泄露 | 环境变量注入；AES-GCM 加密 TOTP；日志不打印凭据 |
| 开放重定向 | OAuth 回调只重定向到固定的前端路径；state 单次有效并绑定 HttpOnly Cookie |

## 3. 关键实现细节

- `Authorization` 决策的每个输入都来自服务端事实；`Scope{All:true}` 只在 grant 与 boundary 同时允许时生效。
- 无效/过期/未激活 grant 不参与 allow；deny 不受会话激活影响，只要有效期命中即拒绝。
- 角色继承在写入和决策读取时都验证无环。
- 管理员邮箱字段按 `identity.user.contact.read` 单独授权；无权限时返回空字符串，而不是遮罩字符串。
- 列表与概览在 SQL 计数/分页前应用 allow 与 deny；邮箱关键词检索也要求完整联系方式读取权限。
- 导出下载检查当前会话、任务归属、导出权限、policy/session-role revision 和授权有效期；权限变化后必须重新导出。CSV 公式前缀被转义，文件名经过 `filepath.Base`。
- 内部 gRPC 只接受数据库接入客户端凭据，不保留静态令牌旁路。资源授权验证调用方 service_owner、资源 owner 和执行点；会话撤销需要用户会话证明，禁止跨用户/应用。
- 错误不返回内部 SQL/驱动信息。JSON 请求上限 1 MiB，未知字段拒绝；ProtoJSON 保留 64 位整数精度。
- MySQL 或 Secure Cookie 配置要求三个安全密钥至少 32 字节并拒绝开发样例；配置 Redis 后连接失败拒绝启动。只有未配置 Redis 的开发环境使用内存临时状态。
- TOTP/恢复码与会话角色使用 CAS；MFA 清空状态时保留 revision，防止删除重建后的 ABA 竞态。密码、邮箱和 MFA 变更使旧近期证明失效。
- console 邮件仅记录收件人和主题；邮件正文、验证码及 SMTP 错误原文不写日志。配置读取/解密失败不伪装投递成功。
- 纯 OAuth 账号的 `mode=verify` 只接受当前已绑定身份；主认证证明与完整 Step-up 分离，均绑定会话和身份版本。主认证证明可用于首设密码或 MFA，有 MFA 时仍必须验证当前第二因素。
- 登录与验证码限流使用固定窗口计数，窗口边界最多允许两倍突发；这是可用性与实现复杂度的取舍，不是绕过（同一账号仍有 MFA 锁定与密码校验）。
- 管理写操作的 `reason` 在服务层强制非空（≤512 字符），不再由代码填充默认值；审计中的理由即操作者输入。
- 资源级授权解释（`resource_id`）不在平台解释接口内计算：资源事实属于资源 owner，接口会显式拒绝而不是返回不完整结论。

### 3.1 组织域隔离（V2.3）

- 授权上下文 `platform` / `organization:{id}` 严格分离：平台决策不加载组织角色，组织决策不加载平台角色；权限的 `context_types` 不含请求上下文时直接拒绝。
- 组织端点的 `{id}` 是唯一租户选择器；路径外传入的角色/分配 ID 必须命中同一 `context_id`，否则按 `RESOURCE_NOT_FOUND` 处理。
- 自定义组织角色只能授予 `context_types` 含 `organization` 的权限，只能使用 allow；`org_` 前缀与内置角色不可修改或归档，内置角色只能通过成员角色接口调整。
- 成员角色变更同步内置角色分配，成员移除/退出撤销该组织全部分配；组织内决策不接受会话角色激活，避免跨租户角色借用。
- 组织审计写入 `organization_id`，租户视图按该列过滤；平台审计仍可跨租户读取。
- 平台管理员访问组织端点属于显式治理覆盖，会保留审计记录。**例外：V2.5 新增的职责分离约束
  端点没有这条覆盖**——见 §3.3 与 §4.10，D7 决定不提供任何跨租户入口。
- Step-up 是"再认证"：已绑定 MFA 的账号必须同时提供当前密码与 TOTP/恢复码；未绑定 MFA 的账号
  以重新输入主密码作为可用证明（此时没有更强的第二因素）。平台 `root/admin` 仍受管理员 MFA
  策略约束，未绑定 MFA 时管理端接口保持拒绝。

### 3.2 密码与会话治理（V2.5 S6/S7）

- 密码策略的四个入口（注册、自助改密、验证码重置、管理员设初始密码）调用同一个
  `ValidatePassword`，策略从 `settings.auth` 读取，不存在各写一份的可能。
- 字符类要求统计 `{大写, 小写, 数字, 符号}` 中出现几类，默认 3 类。非 ASCII 字母与数字
  **不计入任何类**：强制"必须含大写"对中文口令没有意义，只会逼出 `Aa1!` 这类弱模式。
  它们仍计入长度。
- 历史校验用 `bcrypt` 摘要（`password_history`），不是明文也不是可逆加密。表在每次写入时
  折叠到策略窗口，行数上界是 `用户数 × 历史条数`。
- 有效期按 `user_credentials.password_changed_at` 计算。该列对存量账号为 `NULL`，语义是
  "年龄未知"，**不会**被判定为过期；下一次改密时写入。开启有效期不会在发版当天锁定任何账号。
- 过期不阻止登录，而是复用已有的 `password_change_required` 闸门：登录响应置位，中间件在
  下一次请求即阻断管理端路由。这样只有一条强制改密路径，不会出现两套并行判断。
- 会话上限按用户统计活跃会话（未撤销且未过期），超限时撤销**最久未活跃**的会话。撤销是
  服务端写 `revoked_at`，被回收设备下一次请求得到 401，而不是仅仅从列表里消失。
- 会话已记录 `user_agent` 摘要（120 字符）与掩码 IP：IPv4 保留前 3 段末段替换为 `x`，IPv6 保留
  前 2 组，**不存完整 IP 明文**。粒度是网段级，用于"是不是同一地点"的判断，不用于精确定位。
- 写接口限流按 `路由类 + 主体` 计数：登录用户按 user id、接入客户端按 client id、匿名才退回 IP。
  认证端点（`/api/v1/auth/*`）**不在**这层限流范围内，它们已有独立的 IP/账号计数器；两层同时生效
  会让一次请求消耗两份预算，也会给调用方留出挑松的一侧绕过的空间。
- 限流后端故障时**放行**（fail-open）并记录依赖不可用指标：限流是防滥用，不是可用性边界，
  因 Redis 抖动而拒绝所有写请求是更严重的故障。

### 3.3 组织域职责分离（V2.5 S12）

- 角色在**一张表**里全局自增，因此平台约束与组织角色永远不会撞上同一个 id。这是隔离的**根基**，也是不能随便改动的东西：一旦角色 id 改成按上下文各自分配，平台约束就会开始影响租户决策。
- 但隔离**不依赖**这个巧合：`ListConstraints(ctx, tx, authCtx)` 与 `DelegationFilter.Context` 都强制按上下文过滤，`ConstraintsForContext` 再做一次纯函数过滤。三层任意一层都能独立挡住串上下文。
- 组织约束只能引用**本组织**且未归档的角色。跨上下文引用返回 400（不是 403）：允许它等于让租户通过"定义规则"影响平台决策，这是提权。
- 跨租户的约束 id 一律 404。返回 403 会确认"这个 id 在别处存在"。
- `max_roles` 是**按 `role_ids` 范围**计数："最多同时持有下列角色中的几个"，不是"某人总共最多几个角色"。内建角色不在列表里就不参与计数，因此无需为组织域另定口径。`role_ids` 为空的约束在校验里被整条跳过，API 因此拒绝这种形态（存下来什么也不做最危险）。
- 成员**不能给自己授权**（`ORGANIZATION_SELF_GRANT`）。没有这条，"组织自己定约束"+"自己能加角色"等于约束形同虚设。
- 分配与撤销都执行**能力边界**：仅有 `organization.iam.assignment.manage` 不等于拥有目标角色授予的
  能力。落入条件与平台一致——要么自己已持有目标角色的全部 operation，要么存在本组织内、覆盖
  （目标用户、目标角色、动作、有效期、授权上限）的有效委派；否则 `DELEGATION_REQUIRED`。平台委派
  与其他组织的委派因 context 过滤而不参与匹配。
- 组织 SoD 与决策使用**同一个有效期口径**（`assignmentHolds`：未撤销、已开始、未过期、角色仍启用）。
  只判 `Revoked` 会把自然到期的历史分配算作"仍持有"，导致互斥角色永远无法再授予，也把成员的组织
  请求永久判为违规。
- 收紧约束会让现有违规分配**立即失效**（组织权限每次请求重算，不读会话激活角色），因此写入前必须回传 `violating_assignments` 并要求 `acknowledge_violations`；不自动撤销任何分配。
- 移除成员时，其在本组织的角色分配与**双向**委派（作为 manager 与作为 target）一并软失效。只处理 manager 侧会留下一条仍可向该成员授权的通道。target 侧按 JSON 中的**精确用户 ID**匹配（不是子串），manager 侧只失效该用户**亲自创建**的委派并保留 `created_by`——共享角色的其他持有者不会因某人退出而失去自己的委派。

## 4. 已知限制（必须在上线评审中确认）

1. **OAuth 真实提供方尚未做生产沙箱验收**：GitHub/Google 适配器、state、绑定与登录流程已实现并有 mock 测试；上线前必须用真实 Client ID/Secret、HTTPS 回调和账号完成一轮验收。
2. **委派只约束角色分配/撤销**：委派校验覆盖目标角色、目标用户范围、动作、有效期与授权上限（`grant_ceiling`）；通过委派不能修改角色 Grant、继承或创建角色，策略变更仍要求直接权限。平台侧拒绝路径的 HTTP 用例见 `internal/server/delegation_boundary_test.go`。组织域的委派读写入口已在 V2.6 阶段①交付（见 §4.10）；委派仍不能修改角色 Grant、继承或创建角色。
3. **Outbox 为至少一次投递**：消费端按 `event_id` 去重；有订阅客户端时必须配置 `OUTBOX_SIGNING_SECRET`，为空则拒绝投递。队列按订阅方读取未入队历史事件，并使用可过期领取租约，进程中断后可恢复。
4. **审计读取本身不写审计**：当前只记录写操作与安全事件；有读取审计需求时需增加相应实现。
5. **组织域隔离的边界**：V2.3 已把角色、分配、审计收敛到 `organization:{id}` 上下文，组织查询在 SQL 层强制携带上下文。平台 `root/admin` 仍保留跨租户治理覆盖（这是设计选择，不是绕过），**但 V2.5 的职责分离约束端点除外**（D7：非成员一律 404，平台约束列表也只返回平台规则）。组织成员列表、成员角色和部门仍以 `organization_id` 逻辑分区，未做独立库/表分区或行级安全（RLS）。
6. **同步导出**：单次最多 100000 行，生成期间占用请求；超大导出需异步任务。
7. **管理员邮箱变更依赖新邮箱可达**：验证码发送到新邮箱，管理员权限 + Step-up 防止误操作，但无法证明旧邮箱归属；需要旧邮箱确认的场景应走用户自助流程。
8. **OIDC 登出的 front-channel 语义**：RP-initiated logout 使用浏览器顶层 GET 跳转，任何持有公开 `client_id` 与已注册登出回调的页面都能让已登录用户登出（logout CSRF），并可向其回调注入任意 `state`。这是协议固有行为，本服务不额外加确认页；依赖登出的应用应把 `state` 当作不可信输入。
9. **组织创建只有数量配额，没有审批流**：`settings.organization` 默认关闭配额；开启后限制每用户组织数（平台管理员豁免），但不提供企业审批或白名单。需要审批流时应另行设计。
10. **组织域 SoD 的边界（V2.5 + V2.6 已完整交付，仍有三个限制）**：
    - **跨上下文 SoD 不存在**。"同一人不能既审批又付款，不论在哪个租户"用角色组合表达不了，
      需要把约束对象换成 operation 集合，属于另一个模型（见设计文档 §4.3）。
    - **约束只校验角色组合，不校验实际能力**。两个角色若通过授权内容重叠而实际等价，
      互斥约束仍会把它们当作两个不同角色。语义就是"角色对"，不是"权限对"。
    - **平台管理员没有组织约束/委派入口**（含跨租户只读）。紧急处置走组织 owner 账号；
      这是刻意的，避免留下绕过租户治理的通道。

    组织委派的写入入口（设计 §12 的 P4/P5）**已交付**：4 个组织端点与管理界面。写入侧强制
      `organization.iam.constraint.manage`（仅 owner）、Step-up、`reason`、两道 CAS、组织审计、
      Outbox 与 policy revision bump；管理/目标角色必须同属本组织且 active，授权上限不得超过
      创建者在本组织持有的能力（因此不能借委派写入平台操作）。求值侧仍按 `DelegationFilter.Context`
      强制过滤，平台委派与其他租户的委派无法批准本组织的分配。实现期修正 F10：设计 §9 要求的
      "manager 角色必须在创建者活跃角色集合内"不再在写入侧重复——该约束由求值侧
      `checkOrgDelegation` 保证，写入侧重复会让 owner 只能以 `org_owner` 为 manager，使委派分支永远不可达。
11. **密码策略只作用于"设置密码"这一刻**：存量弱密码不会在升级后被强制更换，也无法在登录时
    识别（无法在不持有明文的前提下判断强度）。需要强制轮换时只能开启有效期，且有效期从下一次
    改密开始计时 —— 存量账号的 `password_changed_at` 为空，不会被计入过期。
12. **OpenAPI 不包含浏览器安全方案与原始路由**：Cookie/CSRF、OAuth start/callback、CSV 下载在 `docs/api.md` 中约定，不在 `openapi.yaml` 的 securitySchemes 中。`/scim/v2/*` 同样是原始路由，其 Bearer 方案在 `docs/scim.md` 中约定。
13. **SCIM 只隔离成员资格，不隔离全局账号**：`users` 表仍是全局共享的，SCIM 的 `active=false` 与 `DELETE /Users/{id}` 只影响该组织的成员资格与外部标识映射，不动全局账号。因此一个租户的 IdP 停用某账号不会波及其他租户；反过来，账号级别的物理隔离也不由 SCIM 提供（属 V2.6 阶段④）。邮箱已存在但不属于本组织时供给被拒为 `409`，避免跨租户静默绑定。SCIM 协议子集、`/Bulk` 与 `sort` 等未支持能力见 `docs/scim.md` §4。
